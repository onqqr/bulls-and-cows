# DESIGN.md

## Структуры данных и алгоритмы

### Состояние игры и история

Состояние раунда лежит в `GameState` (`src/core/gameState.ts`). Там настройки (`length`, `base`), секрет строкой (чтобы `0123` не потерял ноль), статус `playing` / `won`, история попыток и таймстемпы.

История — обычный массив `Attempt[]`: попытка + bulls/cows. Старые записи не трогаем. новая попытка добавляется так:

```ts
history: [...state.history, entry];
```

то есть новый массив, без `push` по старому стейту

рекорды — общий список `ScoreRecord` в `src/core/records.ts`. в каждой записи свои `length`/`base`, чтобы в одной таблице было видно при каких настройках сыграли. сортировка: сначала меньше попыток, при равенстве — быстрее по времени. в браузере пишем в `localStorage`, в тестах подсовываем фейковое storage

### evaluateGuess

файл `src/core/evaluateGuess.ts`

сначала оба числа приводим к нижнему регистру и разбиваем на массивы символов

bulls — `filter` по индексам где цифра совпала на месте  
cows — `filter` где цифра есть в секрете (`includes`), но индекс другой

ручных циклов со счётчиками нет, только методы массивов. у нас цифры уникальные, так что одна и та же цифра не будет и bull и cow сразу

### countPossibleSecrets

файл `src/core/countPossibleSecrets.ts`

считаем сколько вообще бывает секретов: перестановки без повторов, с нулём в начале тоже можно. это `P(base, length)`

рекурсия простая:

```text
count(length, base) = base * count(length - 1, base - 1)
если length === 0 → 1
если length > base → 0
```

сверху мемоизация через `Map`, ключ вида `length:base`. иначе при каждом открытии настроек гоняли бы одно и то же заново

## Сложность (Big O)

n — длина секрета/попытки, b — основание системы (размер алфавита). в игре n максимум 6, b максимум 16, но пишем в общем виде

### generateSecret — O(n · b) по времени, O(b) по памяти

делаем пул из b цифр и n раз достаём случайную через `splice`. `splice` может сдвинуть до O(b) элементов, поэтому в сумме roughly O(n · b). пул занимает O(b)

### evaluateGuess — O(n²) по времени, O(n) по памяти

два прохода `filter`. для cows на каждый символ ещё `includes` по секрету → в худшем O(n) на вызов, итого O(n²). для наших маленьких n это нормально, зато код читается как map/filter, а не каша из счётчиков

### isValidGuess — O(n · b) по времени, O(n) по памяти

проверка длины дешёвая. потом проходим по символам и валидируем через алфавит размера b, плюс `Set` на уникальность. в сумме порядка O(n · b)

### countPossibleSecrets — с мемоизацией по сути O(n) на первый расчёт пары (length, base)

без кэша всё равно идём по цепочке из n умножений. с кэшем повторный вызов той же пары — O(1). глубина рекурсии O(n)

## Clean Code — что реально применили

### понятные имена

не `doStuff`, а `generateSecret`, `evaluateGuess`, `isValidGuess`, `submitGuess`. типы тоже по делу: `GameState`, `Attempt`, `ScoreRecord`

### маленькие функции / одна задача на модуль

валидация отдельно, генерация отдельно, сравнение отдельно, стейт отдельно, рекорды отдельно. ui тоже порезан: settings / game / scores, а `index.ts` только склеивает

### логика без DOM

в `src/core` нет document/localStorage напрямую. для рекордов интерфейс `ScoreStorage` — в проде `localStorage`, в тестах свой объект с getItem/setItem

### DRY

`createDigitValidator` живёт в двух местах:

1. `isValidGuess` — проверить всю попытку
2. `filterDraftInput` в `src/app/actions.ts` — резать ввод на лету

историю и рекорды обновляем одинаково по смыслу: спред нового массива, без мутации

### тестируемость

в `generateSecret` рандом приходит параметром, поэтому в тестах можно подсунуть детерминированную последовательность и не ловить флаки

### проще читаемый код, чем «умный»

evaluateGuess специально через filter, countPossibleSecrets — явная рекурсия + кэш рядом, без магии
